## 一、总体结论

这个项目的**架构骨架是健康的，问题集中在"边界完整性"而非"结构错误"**。

值得肯定的部分（不是客套，是审查中反复验证到的事实）：

- **分层单向、无循环依赖**。领域层（`nvidiakey`、`modelcatalog`、`observability`、`database`、`crypto`）不反向依赖 `httpapi` 或 `app`。依赖注入大多是窄接口（`clock.Clock`、`runtimeconfig.Provider`），而不是传递巨型对象。
- **依赖树极干净**。Go 直接依赖只有 2 个（`ncruces/go-sqlite3` + `golang.org/x/crypto`），间接 3 个。全栈 `net/http` + 标准库，没有任何 Web 框架。前端生产依赖只有 5 个。
- **SQLite 配置专业**。写库 `SetMaxOpenConns(1)` + `_txlock=immediate` + `busy_timeout=5000`，读库 `mode=ro` 独立连接池（`min(4, NumCPU)`），WAL + `foreign_keys=ON` + 显式 pragma 校验（`internal/database/db.go:21-66`、`reader.go:16-62`）。读写分离在 WAL 下真正并行。
- **可观测性离线化设计正确**。`BufferRecorder` 队列满时 `select-default` 丢弃并计数，绝不阻塞请求热路径（`internal/observability/buffer.go:165-179`）；Prometheus 导出无动态 label，基数天然受控。
- **凭据处理有意识**。主密钥不落盘（仅运行时注入）、敏感字段 AES-256-GCM 加密、`crypto_sentinel` 防错密钥静默损坏、管理员密码仅走 stdin 不进 argv、`recover` 中间件在顶层。
- **CI 门禁覆盖面广**。gofmt / vet / test / `-race` / golangci-lint / 前端 lint+typecheck+vitest+build / dist 静态闭包检查 / 容器凭据泄漏扫描 / Playwright E2E 都有。

**主要问题归结为三类**：

1. **发布链路的可回滚性被"架构革新"击穿**——从 Docker 版本化 Release 切到原生二进制后，新脚本丢掉了备份与回滚，这是当前**风险最高的一项**。
2. **停机与并发边界的等待语义不完整**——多个后台 goroutine 未纳入优雅关闭的等待集合，且在"写库窗口"与"关库"之间存在竞态。
3. **代理池的失败判定缺少与 HTTP 侧对称的防抖**——传输层失败无时间窗，在出口数量极少的场景下可能被并发抖动瞬时清空。

### P0-2 停机时未等待能力探测与 OCF 同步退出，存在"关库后写库"竞态

**证据**：`internal/app/app.go:346, 363-366` 与 `internal/app/shutdown.go:89-151` ✅ 已复核

`finishShutdown` 显式等待的后台组件：`modelHealthDone`（93-100）、`cleanupDone`（111）、`healthDone`（120）。但：

- `models.StartOpenCodeFreeSync(rootCtx, time.Hour)`（app.go:346）内部会调用 `SyncOpenCodeFreeModels` → `SetEnabled` **写库**，**没有 done 通道**。
- `capabilityProbe.Start(rootCtx, ...)`（app.go:363-366）内部 `TestModelAutoDetailed` → `applyProbeReasoning` / `applyProbeTools` **写库**，同样**没有 done 通道**。

### P0-3 代理池传输层失败判定无防抖，可被并发抖动瞬时清空整个池

**证据**：`internal/xkproxy/pool.go:574-616`（`ReportFailure`）对比 `656-719`（`ReportHTTPFailure`） ✅ 已复核

两个函数的防护等级不对称：

| 防护机制 | `ReportHTTPFailure`（HTTP 失败） | `ReportFailure`（传输失败） |
|---|---|---|
| 时间窗内重置计数 | ✅ 有（694-696，`httpFailureWindow`） | ❌ 无 |
| 全池最近有 2xx 才允许淘汰 | ✅ 有（670，`canEject`） | ❌ 无 |
| 529 过载信号单独处理 | ✅ 有（663-667） | ❌ 无 |
| 计数饱和防无界增长 | ✅ 有（688-690） | ❌ 无 |

`ReportFailure` 每次调用无条件 `HealthFails++`；达到 `FailureLimit`（默认 3）即 `EjectionCount++`；超过 `MaxEjections`（默认 3）即**永久移除并拉黑 5 分钟**（604 行 `p.removed[proxy.Key()]`）。

**为什么这在当前部署下是真实风险**：`memory.md` §28 记录当前星空套餐 `qty=2`，即池中健康出口极少。一次上游百毫秒级抖动若命中十几个并发请求，这些请求在同一瞬间各自 `HealthFails++`，足以在数毫秒内击穿 `MaxEjections`，把仅有的可用出口送入永久黑名单 —— **一次瞬时抖动放大成全池无出口**。

**建议**：给 `ReportFailure` 加与 HTTP 侧对称的时间窗（同一窗口内多次传输失败只计一次），或引入"至少有一个出口近期成功"的门控（复用 `hasRecentRequestSuccessLocked`）。注意 `ReportHTTPFailure` 的注释解释了为何不对 529 淘汰——同样的"全池同时失败 ≠ 单个出口坏"逻辑，对传输失败同样成立。

### P1-1 Transport 缓存 Rebuild 路径并发覆盖，导致 transport 孤儿化与连接泄漏

**证据**：`internal/xkproxy/manager.go:305-327` 对比 cache-miss 路径 `356-359` ✅ 已复核

Rebuild 路径在锁外构造 `transport2`（305 行），拿到写锁后：

```go
// Double-check entry still same.
if cur, ok := m.transports[key]; ok && cur.transport == transport {  // 316
    cur.transport.CloseIdleConnections()
}
newEntry := &cachedTransport{transport: transport2, ...}
m.transports[key] = newEntry                                          // 321: 无条件覆盖
```

两个 goroutine 同时 rebuild 时：A 先写入 `transport2A`；B 进入第 316 行时 `cur.transport`（已是 A 的）`!= transport`（B 读到的旧值），分支跳过，**随后第 321 行直接用 `transport2B` 覆盖 `transport2A`**。A 已把 `transport2A` 返回给调用方，此后它脱离 `m.transports` 管理 —— 既不会被复用，也不会在 `Close()` 或 LRU 淘汰时关闭其空闲连接，**底层 TCP/TLS 连接泄漏**。

对比 cache-miss 路径第 356-359 行有正确的放弃逻辑（若已有 entry，关闭自己新建的 transport 并复用已有的）。Rebuild 路径遗漏了这一步。

**建议**：Rebuild 在第 316 行改为"若已有 entry 则关闭 `transport2` 并返回已有 entry"，与 cache-miss 路径保持一致。

### P1-2 OCF 非流式聚合丢失 `reasoning` / `thinking` 别名，同一上游两种调用形态行为不一致

### P1-3 长流响应每次写 chunk 都分配并拷贝 64KB

**证据**：`internal/observability/http.go:237-251` ✅ 已复核

```go
func (w *trackingWriter) appendTail(payload []byte) {
    _, _ = w.body.Write(payload)
    if w.body.Len() <= usageTailCaptureLimit {   // 64KB
        return
    }
    retained := w.body.Bytes()[w.body.Len()-usageTailCaptureLimit:]
    ...
    kept := make([]byte, len(retained))          // 每个 chunk 分配 64KB
    copy(kept, retained)
    w.body.Reset()
    _, _ = w.body.Write(kept)
}
```

缓冲区一旦超过 64KB 上限，**此后每个 chunk 都触发一次 64KB 堆分配 + 拷贝 + Reset**。一个 1000 chunk 的长流，64KB 之后约 800 个 chunk 各分配 64KB，累计数十 MB 短生命周期垃圾，直接推高 GC 频率。而这只是为了让 `parseUsage` 能读到末尾的 usage 块。

**建议**：只在 `Len()` 超过上限的一定倍数（如 2×）时才裁剪一次，把摊销成本从 O(chunks) 降到 O(1)；或改为固定容量的环形缓冲，避免 Reset/copy 往返。

### P1-4 `Collector.Close()` 无法打断进行中的抓取/验证，最坏阻塞约 27 秒

**证据**：`internal/xkproxy/collector.go:159, 171, 249-331, 425-491, 493-517` ✅ 已复核

`Close()` 在第 507 行 `close(c.done)` 后 508 行 `c.wg.Wait()`。但 `run()` 的调度循环（`165-173`）只在**两次 fetch 之间**监听 `c.done`；进行中的 `fetch(ctx)` 里所有网络调用（`c.upstream.Fetch(ctx)`、`c.validator.ValidateWithLatency(ctx, p)`）与重试等待（327 行 `time.After(validationRetryBackoff)`）**只监听传入的 `ctx`，不监听 `c.done`**。

最坏路径：`validationRetryLimit=3` 次抓取（各 4s 上游超时）+ 3 批验证（各 5s 验证超时）+ 2 次 500ms 退避 ≈ **27 秒**。触发场景是管理员热重载代理配置（`proxySettings.Close()`）或服务退出，此时 Systemd 会认为服务在"卡住"。

**建议**：`fetch` / `validateBatch` 的阻塞点同时 select `c.done`；或在 `Close()` 中先取消一个内部 context 再 `wg.Wait()`。

### P1-5 OCF 代理模式未包装 ReleaseBody，且仅凭响应头就标记出口成功

**证据**：`internal/upstream/opencodefree/client.go:318-348` 对比 `internal/upstream/nvidia/client.go:480`（子代理报告，未逐行复核）

`attemptThroughProxy` 在 `httpClient.Do` 返回后，第 341-342 行对 2xx **立即** `ReportRequestLatency` + `ReportLatency(0)`（清零隔离窗口），并在 348 行直接 `return response, wrote.Load(), err`，**未用 `newReleaseBody` 包装 `response.Body`**。

后果：调用方关闭 body 时不触发 `handle.Release()`；更关键的是，后续长流传输若中断，池层收不到任何 `ReportRequestFailure`，**坏出口不会被减分淘汰**——这正是"快速 502"类问题的温床（`memory.md` §6 有同类排障记录）。

**建议**：对齐 NVIDIA 客户端，用 `newReleaseBody` 包装，并把 `ReportLatency(0)` 的时机从"收到 2xx 头"推迟到"成功读完响应体"。

## 三、中优先级问题

### 装配意图与实现行为冲突：OCF 客户端名存实亡的 `WithProxy`

**证据**：`internal/app/app.go:169-172` 与 `internal/upstream/opencodefree/client.go:290` ✅ 已复核

装配层显式注入代理池并注释说明意图：

```go
// internal/app/app.go:169-171
// The gateway is reached through the same pooled exits as NVIDIA so the
// router's own address stays off the wire on both providers.
openCodeFreeClient.WithProxy(proxy)
```

但客户端内部的条件判断让它在目标 URL 含 `opencode.ai` 时**直接走直连**：

```go
// internal/upstream/opencodefree/client.go:290
if c.local || c.proxy == nil || !c.proxy.Configured() || strings.Contains(c.baseURL, "opencode.ai") {
    ...
    return c.httpClient.Do(request)

```

结合 2026-10-09 的架构收敛（`memory.md` §44：OCF 改为原生直连上游 `https://opencode.ai/zen/v1`，网关容器已移除），这个直连分支**可能是有意保留**的。但那样的话，`app.go` 的 `WithProxy(proxy)` 与其注释就是**误导性的死代码**；反之若意图确为走代理池隐藏出口 IP，则第 290 行的硬编码让该意图静默失效。

这与 `AGENTS.md` 的"池未就绪时必须失败，不得静默直连"是同一个语义边界，**必须二选一并让代码与注释一致**。建议：明确 OCF 是否应走池；若否，删除 `WithProxy` 与相关分支；若是，移除 `opencode.ai` 硬编码判断。

### 全站契约字段：后端 DTO 残留已失效的 reasoning 元数据

**证据**：`internal/httpapi/admin/models.go:71-74, 92-95, 119-122` 与 `web/src/features/models/types.ts` ✅ 已复核

后端三个 DTO（model / candidate / selection）都声明并序列化了 `reasoning_levels`、`reasoning_min_budget`、`reasoning_max_budget`、`reasoning_zero_allowed`、`reasoning_dynamic_allowed`；前端 `types.ts` **零引用这些字段**（findstr 无匹配），也不消费其值。

所以这不是"前端缺功能"，而是**前后端共同遗留的死字段**，仍在 API 响应体、契约快照与前端类型定义中占据位置，增加契约维护面积。**建议**：确认无其他消费方后，删除这批字段、对应的 selection DTO 映射、契约快照与前端类型；同时清理 `AutoReasoningEnabled` 运行时开关。

### 停机整体缺少统一 deadline

**证据**：`internal/app/shutdown.go:43-45, 56-159` ✅ 已复核

`beginShutdown` 用 `time.AfterFunc(grace, a.rootCancel)` 注册兜底取消，但 `finishShutdown` 内部**各组件串行同步等待**（`<-a.recorderDone`、`<-a.modelHealthDone`、`<-a.cleanupDone`、`<-a.healthDone`），没有任何整体 context/deadline 包裹。任一组件排空缓慢（例如 recorder 在 DB 锁竞争下 flush 受阻），整个关闭流程会被拖长，而 `rootCancel` 的兜底只取消后台任务、不会中断这些 `<-chan` 等待。

**建议**：给 `finishShutdown` 传入带 deadline 的 context，各等待点 `select { case <-done: case <-ctx.Done(): }`，超时记日志继续关闭。

### 请求日志批次每次都多跑 2 次外键校验查询

**证据**：`internal/observability/repository.go:101-104, 134-168`（子代理报告，未逐行复核）

每次 batch flush 前 `nullDeletedForeignKeys` 都会对 `access_keys` 与 `nvidia_keys` 各执行一次 `SELECT ... WHERE id IN (...)`。这是为防外键竞态（合理），但代价是**每批固定 +2 次查询**。可改为"只有在 INSERT 真的返回 `FOREIGN KEY constraint failed` 时才降级重试"，把常态路径的开销降为零。

### `model_health_probes` 清理是单条大 DELETE

**证据**：`internal/modelhealth/repository.go:224-235`（子代理报告，未逐行复核）

`request_logs` 的清理有分批（`deleteBatched`，5000 行/批，`observability/repository.go:240`），而 `model_health_probes` 是单条 `DELETE ... WHERE created_at < ?` 全量执行。探测频率高（最小 10s 间隔 × 数十模型）时数据量大，单条大 DELETE 会**长时间独占唯一写连接**，阻塞热路径的日志批次提交。建议改为同样的分批删除。

### `admin_audit_logs` 无清理策略

**证据**：`internal/database/migrations/017_admin_audit_logs.sql:13`（子代理报告，未逐行复核）

其他表都有明确的保留策略（`request_logs` 30 天、`daily_stats` 730 天、`model_health_probes` 14 天、`admin_sessions` 过期清理），唯独审计日志**没有清理或归档**，会单调增长。虽然管理员操作频率低，但自动化探测与反复登录/登出会持续累积。建议加保留窗口或归档导出。

### 冗余 goroutine 监听取消

**证据**：`internal/httpapi/v1/responses.go:215-221`、`internal/sse/proxy.go:61-70`（子代理报告，未逐行复核）

两处都用 `go func(){ select { case <-ctx.Done(): ... } }()` 监听取消，而项目内 `prime.go:48` 已采用 Go 1.21+ 的 `context.AfterFunc`（无额外 goroutine）。高并发慢流场景下这是成百上千个闲置 goroutine。建议统一改用 `context.AfterFunc`。

### SSE 数据帧重复反序列化

**证据**：`internal/httpapi/v1/chat.go:351-359` 与 `internal/observability/reasoning.go:149-179`（子代理报告，未逐行复核）

单个 SSE data 事件在流式路径上被 `json.Unmarshal` 多次：`completion.observe`（1 次）+ `ReasoningDeltaChars`（命中字段后再 1 次）+ 首帧探测（`semanticChatEvent` 1-2 次）。可合并为一次结构体解析，减少长流场景的 CPU 与分配。

### SSE 编码器无条件做全串换行归一化

**证据**：`internal/sse/encoder.go:59-71`（子代理报告，未逐行复核）

`Encode` 对每个事件的 data 无条件执行两次 `strings.ReplaceAll`（`\r\n`→`\n`、`\r`→`\n`）再 `strings.Split`。绝大多数 data 不含 `\r`，却每次都完整遍历并新建字符串。建议先 `bytes.IndexByte(b, '\r')` 快速判断，仅在命中时走慢路径。

### `normalizeChatBody` 未启用 `UseNumber`，大整数会丢精度

**证据**：`internal/upstream/opencodefree/fingerprint.go:76-120`（子代理报告，未逐行复核）

用 `map[string]any` 反序列化再序列化请求体但未 `UseNumber()`，JSON 中的大整型（雪花 ID、纳秒时间戳、工具参数里的数值）会被解析成 `float64`，可能变成科学计数法或丢精度。建议改用 `json.Decoder` + `UseNumber()`，或只对需要改写的字段做定向处理。

### 全局 body 预算信号量影响测试隔离

**证据**：`internal/httpapi/v1/bodybudget.go:36-37` ✅ 已复核（降级说明）

`bodyReadSemaphore`（16 槽）与 `inFlightBodyBytes` 是包级全局变量。**从代码注释看这是深思熟虑的设计**（第 21-30 行记录了从 1MB 降到 64KB 占位、并配 `chunkedBufferPool` 复用 256KB 读缓冲以降低 GC，明显做过 pprof 调优），**生产行为没有明显缺陷**。问题在于全局单例使并发测试相互踩踏、无法为特定 handler 注入独立容量。属于可维护性问题，不建议为"修复"而牺牲现有设计。

## 四、架构级观察（非缺陷，但影响长期维护成本）

### 1. Chat 与 Responses 双路径的重复执行骨架

`internal/httpapi/v1/chat.go:131-186` 与 `responses.go:122-178` 的 attempt 执行闭包重合度约 85%（粘性会话注入 → 调用 → 状态码校验 → 流式 `primeSSE` / 非流式 `ValidateNonstreamChat` → reasoning 观测 → 思考饥饿检测 → 标记完成），仅 Responses 末尾多一步 `FromChatWithConfig` 转换。OCF 路径同样有约 75% 重合（`chat.go:196-246` 与 `responses_opencodefree.go:18-72`）。

这类重复的危险不在当前代码量，而在**未来修复只改一侧**——项目历史上已经出现过同类问题（`memory.md` §34 记录的"两套 retry/status 生命周期"就是为此做的第一阶段收敛）。建议继续按 `request_prepare.go` 的模式，把执行骨架收敛为一个共享执行器，Responses 作为后置转换装饰器。

### 2. 大型函数与参数列表

超过项目自身 40 行规范的核心函数：`sse/proxy.go:53-230`（178 行）、`httpapi/v1/audio.go:48-179`（132 行）、`router/attempt.go:132-244`（113 行）、`chat.go:317-420`（104 行）、`protocol/responses/request.go:35-137`（103 行）。参数过多：`router.NewAttempt`（7 个依赖）、`responses.go:89`（7 入参）。这些函数内交织了校验、I/O 超时、重试、转码与指标，圈复杂度高且难以单测。建议引入参数对象并按职责拆分。

### 3. 前端严重超长的视图组件

`ModelsView.vue` 1050 行（数据获取 + 候选发现 + 任务轮询 + 并发测试 worker + 筛选 + 双份多选状态同步 + 220 行渲染）、`ModelHealthView.vue` 707 行（内嵌 5 维排序算法与分组逻辑）、`StatisticsView.vue` 678 行（三接口并发编排 + 命令式操纵子组件私有状态 + 手写分页器）。建议按功能提取 composable（`useModelTestJob`、`useModelHealthFilter`）与子组件，让排序/分组等纯逻辑可以脱离组件做确定性测试。

### 4. 前端数据获取模式分裂

仅 4 个视图使用共享的 `shared/useAsyncData.ts`，另外 5 个（`ModelHealthView`、`StatisticsView`、`RuntimeView`、`AuditView`、`ProxyPoolView`）各自手写 `loadSequence` / `AbortController`。其中 `ProxyPoolView.vue:66-89` 有 abort 但**缺 `loadSequence` 序号防护**，网络抖动时慢的旧响应可能覆盖新状态。建议统一到 `useAsyncData`。

### 5. 缺失前端全局错误边界

`web/src/main.ts` 未配置 `app.config.errorHandler`，也未监听 `unhandledrejection`。未捕获异常会导致静默白屏，操作员无从得知。建议加全局兜底并接入 toast。

### 6. 双份 DOM 树并行挂载（中度，非"严重"）

`ModelsView.vue:863-895`、`AccessKeysView.vue:164-177`、`NvidiaKeysView.vue:357-372` 同时挂载桌面表格与移动卡片，靠 `hidden md:block` / `md:hidden` 切换。**这是常见且可接受的取舍**（换取零切换闪烁、避免 JS 断点监听），代价是移动端组件也被实例化。若这些视图的移动端卡片确实重（如 `ModelCards` 305 行），可考虑用 `useMediaQuery` 条件渲染；否则不建议为此增加复杂度。

### 7. 契约测试覆盖断层

`web/src/shared/api/contract.spec.ts` 只覆盖 17 个旧快照用例，**7 个核心接口零覆盖**：`/admin/api/providers`、`/admin/api/audit-logs`、`/admin/api/model-test-jobs`、`/admin/api/models/candidates/test`、`/admin/api/proxy-pool/status`、`/admin/api/auth/*`、`/admin/api/events/stream`。而前后端契约是**四处手工维护**（Go DTO、TS 接口、视图内运行时类型守卫、契约快照），漂移风险已在第三节的 reasoning 字段上具体发生。

### 8. 工程化缺口

- **CI 重复执行全量测试**：`ci.yml:79` 跑 `go test ./...`，`ci.yml:82` 又跑 `go test -race ./...`（后者已包含全部用例），将测试时间白白翻倍。建议只保留 race 那一轮。
- **无覆盖率门禁、无依赖漏洞扫描**：未生成 coverage 报告，也没有 `govulncheck` / `pnpm audit` / 镜像 CVE 扫描。
- **CI 与生产路径脱节**：CI 仍以 Docker 构建与 Compose 验收为主（`ci.yml:119-124`），而生产已全面转向 Systemd 原生二进制。CI 验证的基础设施与线上运行方式不一致。
- **无 `.golangci.yml`**：`golangci-lint run ./...` 全用默认规则（`ci.yml:66` 的注释显示曾因缺配置导致 gofmt 规则失效，才手写补丁）。
- **测试中的硬编码 `time.Sleep`**：`sse/idle_test.go:96`(120ms)、`observability_test.go:183`(100ms)、`nvidiakay/proxy_client_test.go:220`(200ms) 等，在高负载 CI 上有 flaky 风险，建议改用 channel 通知或项目已有的 `clock.Clock` 虚拟时钟。
- **全仓零 `t.Parallel()`**，测试纯串行。
- **废弃的 Docker 部署脚本仍在 `scripts/deploy/`**（`deploy_remote.py`、`deploy-public.sh`、`rollback-public.sh`），生产已无容器，易被误执行。建议归档。

### 9. 测试缺口（关键路径）

以下路径**缺乏测试**，与它们的风险等级不匹配：

- 代理池在并发大量传输失败下的淘汰行为（`xkproxy/report_failure` 语义）。
- OCF 流式聚合遇到"半开中断"（未发 `[DONE]` 且 TCP 重置）时的错误传播。
- 高并发下 `RetryBudgetMS` 被同时消耗时的排队/背压行为。
- 下游慢客户端（slow consumer）对 SSE 缓冲上限与超时切断的防护。
- 限流在进程重启后的持久化边界（`adminauth/ratelimit_test.go` 只测内存路径）。
